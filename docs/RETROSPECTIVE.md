# 프로젝트 회고

[← README로 돌아가기](../README.md)

---

이 프로젝트를 진행하면서 단순히 LLM에게 Prompt를 전달하는 것과, LLM이 실제 업무를 안전하게 처리하도록 시스템을 설계하는 것은 다른 문제라는 점을 배웠습니다.

## 1. LLM에게 모든 책임을 맡기지 않기

LLM은 자연어 이해와 Tool 선택에는 강하지만 정확한 계산과 데이터 정합성까지 전적으로 맡기기에는 위험합니다.

따라서 금액 계산, 입력 검증, 주문 상태 확인, 중복 환불 차단, DB 저장은 일반 서버 코드가 담당하도록 했습니다.

## 2. 자연어 이해와 실제 데이터 처리를 분리하기

`"3만원대 신발"`이라는 표현을 이해해 가격 범위와 키워드를 추출하는 일은 Agent가 담당합니다.

추출된 조건을 검증하고 실제로 어떤 상품이 해당 조건을 만족하는지 판별하는 일은 ProductService와 ProductRepository가 담당합니다.

```text
자연어 해석
→ Agent

구조화된 조건 검증
→ Service

실제 DB 검색
→ Repository

검색 결과 설명
→ Agent
```

이 구조를 통해 LLM의 자연어 처리 능력을 활용하면서도 정확한 숫자 비교와 데이터 검색은 서버가 담당하도록 분리했습니다.

## 3. 같은 모델도 역할에 따라 별도 인스턴스로 구성하기

Agent와 RAG는 모두 `gemini-2.5-flash-lite`를 사용하지만 담당하는 역할은 다릅니다.

Agent LLM은 Tool 7개가 연결된 상태로 고객의 요청을 해석하고 필요한 Tool을 선택합니다. RAG LLM은 Tool 없이 검색된 정책 문서를 기반으로 텍스트 답변만 생성합니다.

모델 이름이 같더라도 필요한 기능과 책임이 다르기 때문에 각각 별도 인스턴스로 구성했습니다.

## 4. 기능뿐 아니라 실패 흐름도 함께 설계하기

정상적으로 처리되는 요청뿐 아니라 다음과 같은 상황도 함께 고려해야 했습니다.

* 필수 정보가 부족한 경우
* 정책 문서에 답이 없는 경우
* 지원하지 않는 요청인 경우
* 다른 고객의 주문을 조회하려는 경우
* 같은 환불을 다시 요청하는 경우
* 여러 Tool이 동시에 같은 DB Session을 사용하는 경우

Agent가 자동으로 처리할 수 없는 문의는 오류 메시지만 반환하지 않고 문의 티켓으로 저장해 후속 처리가 가능하도록 구성했습니다.

## 5. 계층별 책임을 명확하게 나누기

Repository, Service, Tool, Agent Node, Graph가 각각 무엇을 담당하는지 구분하지 않으면 검증과 예외 처리가 여러 곳에 중복될 수 있습니다.

```text
Repository
DB 조회와 저장

Service
업무 규칙과 트랜잭션

Tool
Agent가 호출할 인터페이스와 결과 형식 변환

Agent Node
고객 요청과 Tool 결과를 해석하고 다음 행동 결정

Graph
Agent Node와 Tool Node 사이의 실행 흐름 관리

AgentService
요청별 의존성 조립과 Graph 실행
```

## 6. 실제 사용자의 표현을 기준으로 기능 설계하기

상품 검색은 정확한 상품명만 입력하는 상황을 기준으로 만들지 않았습니다.

사용자는 색상·브랜드·종류·특징·가격대를 조합해 자연어로 요청할 가능성이 높습니다.

```text
"빨간 나이키 신발"
"3만원대 운동화"
"파란색 반팔"
"5만원 이하 상품"
```

이러한 표현을 실제 검색 조건으로 연결하기 위해 Agent의 자연어 이해와 서버의 구조화된 검색 기능을 함께 사용했습니다.

## 7. 동작하는 코드에서 끝내지 않고 판단 기준 남기기

기능을 구현하는 것만으로 작업을 끝내지 않고, 문제가 발생한 원인과 선택한 해결 방법을 기록했습니다.

이를 통해 다음 프로젝트에서도 재사용할 수 있는 판단 기준을 축적하고자 했습니다.

> LLM은 고객의 의도를 파악하고 Tool을 선택한다.
> 자연어를 구조화된 조건으로 변환하는 일은 Agent가 담당한다.
> 서버는 업무 규칙과 데이터 정합성을 책임진다.
> Repository는 DB에 접근하고 Service는 업무 단위의 트랜잭션을 관리한다.
> 같은 모델이라도 역할과 필요한 기능이 다르면 별도 인스턴스로 구성한다.
> 처리하지 못한 요청도 시스템에서 사라지지 않도록 보존한다.

## 8. 모든 기능이 Agent를 거칠 필요는 없다

관리자 기능(문의 상태 변경, 주문·환불 조회)을 만들면서 처음엔 기존
AgentService의 조립 로직을 그대로 재사용하고 싶었습니다.

하지만 관리자 작업은 자연어 해석이나 여러 턴에 걸친 대화가 필요 없는
단순한 조회·상태 변경이었습니다. LangGraph와 Tool Calling을 거치는 구조는
오히려 불필요한 LLM 호출과 Tool 선택 과정만 추가할 뿐이었습니다.

그래서 admin_router.py는 Agent·Graph·RagService·Tool을 전혀 거치지 않고
Service 계층을 직접 호출하도록 설계했습니다. Repository/Service 조립
순서는 agent_service.py와 동일하게 재사용하되, RagService와 Tool 조립
부분만 제외했습니다.

기능을 하나 만들 때마다 "이 요청이 정말 LLM의 자연어 해석을 필요로
하는가"를 먼저 판단하는 습관이 이번에 생겼습니다.

## 9. 코드 재사용과 계층 분리 사이의 트레이드오프

graph/tools.py에는 이미 KST 변환(`_format_order_time`)과 상품 요약
(`_item_summary`) 로직이 있었습니다. admin_router.py에도 똑같은 로직이
필요했지만, tools.py를 import하지 않고 같은 로직을 admin_router.py에
별도로 다시 구현했습니다.

tools.py는 langchain_core에 의존하는 Agent 전용 모듈입니다. 관리자
기능이 여기 의존하게 되면 "관리자는 Agent를 거치지 않는다"는 설계
원칙과 실제 의존 관계가 어긋나게 됩니다. 코드 몇 줄이 두 파일에
중복되는 것을 감수하고, 계층 간 의존 방향을 지키는 쪽을 선택했습니다.

이건 정답이 정해진 문제는 아니라고 생각합니다. 중복이 더 늘어나면
공통 유틸리티 모듈로 분리하는 것도 고려할 수 있습니다.
